A toilet-bowl consolation bracket for the 8 teams that miss the playoffs in a 16-team Yahoo fantasy baseball league — built because Yahoo has no support for this format at all.

01 — Overview

Why this exists

Scott runs a 16-team H2H-categories Yahoo league with an 8-team playoff. The 8 teams who miss it have nothing to play for down the stretch — and Yahoo doesn't offer a consolation-bracket format at all, in any configuration. This is a small, public, read-only site the group checks from the chat: a toilet-bowl bracket for last place, $50 winner-take-all, money handled off-site.

Format
Seeds 9–16 (worst 8 of 16 teams), single-elim, 3 rounds, re-seeded each round
Season data
Yahoo Fantasy API when access is approved; a fully-parallel manual CSV import path otherwise — the site never knows which one it's reading from
Audience
Public link, no login, no search indexing — a group-chat product, not a public product
Built by
Claude Code (planning, architecture, review) + Codex CLI (delegated implementation), directed by Scott — worth knowing going in, since it explains some of the code's density of comments-explaining-decisions and the paper trail in docs/

03 — Architecture

The core pattern: pure decisions, guarded writes

Every outcome-deciding piece of logic — the category comparator, the tiebreaker chain, re-seeding, the round/seed-lock state machine — is a pure function with no I/O, unit-tested against fixtures. A thin layer of DB-bound "executors" consumes their output and applies it transactionally, with an atomic WHERE status = '<expected>' … RETURNING guard on every write, so two concurrent triggers (a page visit and a cron tick, say) can't double-advance a round or double-settle a result.

Sync model

No cron-only architecture — data pages are force-dynamic, and a visit that finds stale data schedules a sync via Next's after() and still renders instantly from Postgres. An atomic lock claim (UPDATE … WHERE lock_expires_at IS NULL OR < now()) means two simultaneous visits produce exactly one sync. Freshness windows scale with the phase: 30 min during bracket weeks, 6 h during the race, never once a champion is settled. A daily Vercel cron is the backstop.

Round finalization is provisional-first: a Sunday-night close computes a winner immediately and advances the bracket, then a 24-hour correction window re-verifies before marking anything final. If a re-verify flips the winner, the affected branch freezes and goes under_review — results never silently flip; a commissioner has to resolve it.

04 — Security & testing

What's guarded, what's tested

Admin auth

  • bcrypt password verify, HMAC-signed session token, timing-safe comparison, real expiry check
  • HttpOnly; Secure; SameSite=Strict cookie, 7-day expiry
  • CSRF on every mutation route: SameSite=Strict + Origin-header check, belt-and-suspenders
  • Per-IP login throttle — known limitation: in-memory, won't survive across Vercel serverless instances; accepted tradeoff for a single-admin app where bcrypt is the real defense

Test coverage

166 vitest tests — fixture-driven, one file per pure module, plus a single large "dress rehearsal" integration test that drives a full fake 3-week bracket end to end: a head-to-head tiebreak, a stat-correction flip that freezes one branch while the rest keep computing, an admin override, and a champion.

4 Playwright smoke tests in CI (three phases + the admin gate) run against zero real database — an env-gated fixture bypass (E2E_TEST_MODE + a scenario header, double-checked before any DB call is ever reached) lets the app render canned data instead, so CI needs no Neon branch and no new secrets.

06 — For reviewers

If you're reviewing this

Where a code review would add the most value

  • The live-compute logic (matchupCompute.ts / matchupProcessor.ts, Issue 9) is the biggest single piece of business logic and the one that decides real money — it's had a normal review pass, but not yet the deeper adversarial pass planned separately.
  • The security pass (Issue 14 — probing the checklist in the security section against the real deployment) hasn't happened yet at all; it's blocked on Yahoo OAuth landing first.
  • The pure/impure split and the atomic-guard pattern in src/lib/sync/seedLock.ts and matchupCompute.ts are the architectural core — worth checking whether the concurrency guards actually hold up under real load, not just the fixture scenarios the tests cover.
